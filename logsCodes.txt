// REDACTION (every log ID, since 1.9.1)
// storeLog redacts key material from the message, errorInfo and the url label (and frontUrl) right after the error-shape switch,
// before every sink: the console print, the message filters, the debounce key and the backend request. The background storeLogEvent
// proxy (logs sent from content scripts) redacts message and context again. Redaction is idempotent and fails closed.
// A marker carries the kind and the length only, never a fingerprint, hash or excerpt of the key:
//   [redacted:<kind>:<len>]   spki-p256 | spki-rsa | pkcs8-p256 | pkcs8-rsa (DER key header) | pem | hex | b64 | b64url (high-entropy run)
//                             | b64-pct (percent-encoded key) | reason (a value quoted in the backend "cannot update key from X to Y" Reason)
//                             | unprocessable (the redactor itself failed and replaced the whole value; <len> is 'object' for a non-string)
//   [redacted:field:<name>:<len>] / [redacted:field:<name>:object]   a key-named field (public_key, public_signing_key, publicKey, signingPublicKey,
//                             signingPrivateKey, privateKey, device_public_key, pkcs8, spki, jwk) or a JWK member (d, p, q, dp, dq, qi, k, x, y, n)
//   [binary:<n>]              ArrayBuffer / typed array of n bytes
//   [CryptoKey]               a key handle
//   [Circular], [unserializable], [array], [object] are walk placeholders (cycle, throwing getter, depth limit 6), not redactions.
// context.redactions = {count, kinds} on every entry sent (kinds: the marker kinds above plus field, binary, cryptoKey). The payload is
// already clean, but a non-zero count on any log ID means a producer hands key material to storeLog: fix it to log typed fields.
// b64 / b64url / hex are heuristic and can be false positives (e.g. a base64 OAuth state in a page URL); the other kinds need a DER header,
// PEM armor, a key-named field, a JWK member or the backend conflict Reason, so outside that Reason they are real key material.
// Console output of storeLog and of the key-adjacent modules goes through safeConsole, redacted the same way, also with logging off.

64 - signingState - markSigningConflict - signing key conflict: backend already holds a different public signing key, re-pairing required [warning]
     SINCE 1.9.1 THE PAYLOAD IS BUILT FROM TYPED FIELDS, NEVER FROM THE BACKEND ERROR (its Reason names both public keys). No content, Reason, Description or url:
       {message: 'Signing key conflict: backend holds a different public signing key', status, statusText, signed (whether the rejected PUT was signed),
        backendCode (content.Code, number|null), backendType (content.Type from the list in 27's backend.type, 'other', or null),
        cause: {keyGenerations, sendsWithThisKey, keyAgeBucket, recordAttempts, recordAgeBucket, storedExtensionVersion}}
     cause holds counters and enums only (no key, fingerprint or hash):
       keyGenerations          storage.local signingKeyGenerations: signing keys generated in this identity lineage. generateDefaultStorage writes 1; each ensureUsableSigningKeyMaterial regeneration adds 1 (a reuse or a 75 restore does not). A regeneration that replaces a key from before the counters (counter absent or malformed) writes 2: at least that key came before it. null when absent.
       sendsWithThisKey        storage.local signingKeySends as read for the failing PUT: keyed requests (a PUT carrying public_signing_key, a create POST) sent with the current key BEFORE it. 0 = the failing PUT was the key's first send. null when absent.
       keyAgeBucket            age of the current key (signingKeyGeneratedAt): '<1m' | '<1h' | '<1d' | '<7d' | '>=7d' | 'unknown'
       recordAttempts          attempts of the failing pendingBrowserRegistration record (number|null)
       recordAgeBucket         age of that record (firstAttemptAt), same buckets
       storedExtensionVersion  storage.local extensionVersion (a release number like '1.9.0'; 'other' when malformed; null when absent). Only a successful PUT commits it, so on the first keyed PUT after an update it still names the PRE-update version.
     Reading the cause:
       keyGenerations === 1 && sendsWithThisKey === 0 -> the backend held a key before this lineage ever sent its only key: another copy of the identity set it (cloned or rolled-back profile, or a third party).
                                                         The same extensionID repeating 64 across days -> an environment that rolls storage back (non-persistent VDI/Citrix, roaming profile, backup or reboot restore).
       keyGenerations > 1                              -> this install regenerated its key locally; expect a preceding 74 (a loss of both halves regenerates silently, as a first generation).
       sendsWithThisKey > 0 && keyGenerations === 1    -> an earlier send of this same key never reached the backend while another key did (clone / rollback), or a backend anomaly.
       null counters, keyAgeBucket 'unknown'           -> the key predates 1.9.1; sends are counted from its first 1.9.1 send. A lineage without counters that 1.9.1 regenerates over an existing key reports keyGenerations 2
                                                         (a lower bound), so it reads as a local regeneration on its own. Only a first key starts at 1 without a counter: the first signing key of a
                                                         <=1.8.4 install, or a 1.9.0 install that lost both halves (storedExtensionVersion 1.9.0 or later hints at the latter).
     At most once per extensionID: storage.local signingConflictLoggedFor, recorded after the log call (also when logging is off) and wiped with the identity. A new extensionID re-arms it; an install without an extensionID always reports.
     A failed strict signing-state read writes nothing and logs nothing (no conflict flag, no 64, no notification); the next conflicting response retries. Reported on Chrome as well as Firefox: identity copies and storage rollbacks do not depend on the browser.
     Keyless retry (1.9.1): the conflict retry never re-sends the key. The write that resets the pendingBrowserRegistration update record's attempts to 0 also sets keyless: true on it, whether or not markSigningConflict could store the conflict.
       Every PUT for a keyless record goes out without public_signing_key: no key-material check, no signingKeySends count, and a success commits the browser info without activating signing.
       The flag survives backoff retries and every update that enqueueBrowserRegistration merges into the pending record. A 404 converts the record to a create without it (a create POST always carries the key).
       While the conflict could not be stored, only a fresh record sends a keyed PUT again: a later browser or extension update, or ensureSigningKeyRegistration on browser start, once the keyless record has committed or been dropped.
       So an install sends at most one keyed PUT per registration episode, and each gets the conflict again; this 64 and the re-pair notification wait for that episode's conflict.

74 - ensureUsableSigningKeyMaterial - unregistered signing key unusable: kept or regenerated [warning] (new in 1.9.1)
     Message 'Unregistered signing key kept: its public half is unknown, nothing to register' (outcome kept) or 'Unregistered signing key regenerated' (outcome regenerated); cause {reason, outcome, storedIn}, enums only:
       reason: privateMissing (public key stored, private key gone: IndexedDB loss or rollback)
             | publicMissing (the private key survives but keys.signingPublicKey is lost and no pair-verified signingKeyMeta could restore it: storage.local tier, or an IndexedDB key from before 1.9.1 that never got its companion)
             | importFailed (keys.signingPrivateKey is present but does not import; wins over the other reasons)
             | pairMismatch (the stored public key is not the public half of the private key, e.g. a leftover of a 1.9.0 generation race, or a storage.local rollback past a regeneration; when the IndexedDB companion pairs with the key, the public key is restored instead — 75)
       outcome: kept        | FALLBACK, expected never: a private key survived (pairMismatch, publicMissing, importFailed with an IndexedDB key behind the corrupt copy) but its public half could not be recovered from its own signatures (see 75 source=derived — that recovery succeeds for every real P-256 signing key).
                             The backend never replaces a registered key (same key = no-op, another key = 400, no reset) and this may be the registered one, so it STAYS the live key: the mismatched public key is dropped from storage.local, the 'signingKeyUnregistrable' marker is set, no pair is generated and no PUT carries a key.
                             It signs as soon as the backend challenges the install (an unsigned request gets 401 -> signing.challenged), and the first verified success activates signing. Logged once per install (the marker), not on every start. Any volume here is a bug in recoverSigningPublicKey or a key that is not P-256.
              | regenerated | nothing survived (privateMissing, importFailed with nothing behind it), or the key is for a new identity (a create, or the re-registration after a 404, whose row and key are gone): a fresh pair replaced the material before registration.
       storedIn: idb | local (tier of the kept, or of the NEW, private key; local = Safari's keyStoragePolicy, a storage.local pkcs8 survivor, or the IndexedDB-unavailable fallback, which also logs 67)
     Not logged for a first generation (no signing key material at all), nor when a reset replaced the identity in the meantime and nothing was written. Sent after the key-material lock is released.
     No generation at all (so no 74) when keys.signingPublicKey is absent and the IndexedDB read of the signing key fails while IndexedDB still takes writes (a write probe, record 'signingKeyWriteProbe', written and deleted): the read error propagates and the caller retries (63 from ensureSigningKeyRegistration, backoff in flushBrowserRegistration),
       so a transient error never overwrites a key nobody could read. An IndexedDB that takes no writes either (Firefox permanent private browsing) still gets a silent first generation in the storage.local fallback (67).
     Inactive signing only: while signing is active a regeneration is refused (code SIGNING_ACTIVE), except for the create re-registration after a 404, whose row and key are gone.
     Correlate with 64 on the same extensionID: 74 outcome=regenerated then 64 = the backend already held the key this install lost; a 64 with no 74 before it = another copy of the identity, or a third party, set the backend key (see the 64 cause). outcome=kept never leads to a 64: no key is ever sent for a kept survivor.
     Expect NO 74 uptick from mismatched pairs after the 1.9.1 rollout: those recover their public key (75 source=derived) and register or confirm it through the normal keyed PUT; only a lost private key (privateMissing) regenerates and may then draw a 64.
75 - ensureUsableSigningKeyMaterial - signing public key restored: keys.signingPublicKey was lost or mismatched (storage.local rollback, crash, a 1.9.0 stale write) while the private key survived, and the same public key was put back instead of a regeneration [warning] (new in 1.9.1)
     Constant message 'Signing public key restored'; cause {source}:
       companion | the pair-verified signingKeyMeta IndexedDB record (keys generated by 1.9.1+, or older keys whose companion 1.9.1 backfilled on a verified reuse); IndexedDB tier only
